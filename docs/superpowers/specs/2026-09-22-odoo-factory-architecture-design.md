# Odoo Factory ERP Framework & Agent Operating System — Design Specification

**Status:** FROZEN ARCHITECTURE BASELINE (Approach 1.1 — Amended)  
**Date:** 2026-09-22  
**Target System:** Odoo 18.0 Community + PostgreSQL 16 + Docker  

---

## 1. Executive Summary & Goals

Transform the existing monolithic Odoo codebase into a modular, reusable **Factory ERP Framework** with a discrete and mixed manufacturing baseline, extensible via vertical profiles for process industries (apparel, furniture, metals, food, plastics, electronics).

### Key Architectural Tenets
1. **Strict Ownership Boundaries:** Vendor code (`addons/`, OCA/Core) is strictly separated from project-owned custom code (`custom/`).
2. **Flat Custom Addons Root:** Single `custom/` directory for all project-owned addons to ensure native Odoo discovery without recursive filesystem hacking.
3. **Declarative ERP Engine:** Business capabilities, schemas, and install profiles defined declaratively in `.factory/`, backed by auto-generated catalog and dependency graph with cycle detection.
4. **Decoupled Runtime Lifecycle:** Clean separation between continuous server runtime (`docker compose up`), idempotent environment bootstrap (`scripts/bootstrap.*`), and disposable test execution (`scripts/test.*`).
5. **Agent Operating Manual:** Self-contained `odoo-factory-engineer` skill enabling AI agents to implement business requirements across models, views, reports, and workflows with zero context loss.
6. **Continuous Quality & License Awareness:** Automated CI gates, JSON schema validation, licensing compliance (OCA AGPL compatibility), and synchronization of code, tests, docs, and spec-kit.

### Filesystem Ownership Policy
* **`addons/**` (Vendor):** READ-ONLY. Direct edits strictly prohibited. Custom behavior MUST be achieved via inheritance in `custom/`. If an upstream bug fix is unavoidable, it must be documented with an ADR and an architectural exception log.
* **`custom/**` (Project-Owned / Custom):** Primary extension zone. All modules adhere to standard Odoo 18 naming and structure conventions.
* **`.factory/**` (Contracts):** Machine-readable single source of truth for agents and CI.
* **`skills/**` (Agent):** Behavioral guidance instructing agents on how to read `.factory/` and modify `custom/`.

## 3. Docker Runtime Decoupling & Environment Configuration

### 3.1 Environment & Secrets (`.env.example`)
```bash
# Database Settings
POSTGRES_DB=postgres
POSTGRES_USER=odoo
POSTGRES_PASSWORD=odoo_secure_pass
PGDATA=/var/lib/postgresql/data/pgdata

# Odoo Runtime
ODOO_DB=odoo
ODOO_ADMIN_PASSWD=admin_secure_pass
QUEUE_JOB_CHANNELS=root:4

# Localization
FACTORY_COUNTRY=EG
FACTORY_CURRENCY=EGP
FACTORY_CHART_TEMPLATE=eg
```

### 3.2 Clean Runtime (`docker-compose.yml`)
* **Services:** `web` (Odoo 18), `db` (PostgreSQL 16 with health check).
* **Database Healthcheck:**
  ```yaml
  test: ["CMD-SHELL", "pg_isready -U odoo -d postgres"]
  interval: 5s
  timeout: 5s
  retries: 5
  ```
* **Web Dependencies:** `depends_on: db: condition: service_healthy`
* **Web Volumes:**
  * `./addons:/mnt/extra-addons`
  * `./custom:/mnt/custom-addons`
  * `odoo-web-data:/var/lib/odoo`
* **Addons Path:** `/mnt/custom-addons,/mnt/extra-addons/manufacture,/mnt/extra-addons/ddmrp,/mnt/extra-addons/stock-logistics-warehouse,/mnt/extra-addons/stock-logistics-orderpoint,/mnt/extra-addons/server-backend,/mnt/extra-addons/server-tools,/mnt/extra-addons/stock-logistics-workflow,/mnt/extra-addons/web,/mnt/extra-addons/stock-logistics-availability,/mnt/extra-addons/queue,/usr/lib/python3/dist-packages/odoo/addons`
* **Command:** `odoo --load=base,web,queue_job -d ${ODOO_DB:-odoo}` (NO `-i` flag).

### 3.3 Idempotent Bootstrap Script (`scripts/bootstrap.ps1` / `.sh`)
* Distinguishes state:
  * Database exists vs. missing (initializes if missing).
  * Module missing vs. installed vs. requires upgrade.
* Commands:
  * `bootstrap --profile core`
  * `bootstrap --profile operations --demo`
  * `upgrade --changed`
  * `upgrade --module <name>`

### 3.4 Disposable Test Runner (`scripts/test.ps1` / `.sh`)
* Spin up disposable test database: `odoo_test_<run_id>`
* Execute headless test container with `--test-enable --stop-after-init`
* Collect test logs and drop database on completion.

## 4. Metadata Engine Specification (`.factory/`)

### 4.1 Schema Validation (`.factory/schemas/`)
All YAML contracts in `.factory/` are strictly validated against JSON Schemas in CI:
* `project.schema.json`
* `capabilities.schema.json`
* `module_policy.schema.json`
* `install_profiles.schema.json`
* `golden_scenario.schema.json`
* `health_checks.schema.json`

### 4.2 Global Project Contract (`.factory/project.yml`)
```yaml
project:
  name: odoo_factory
  version: "18.0.1.0"
  description: "Generic Universal Factory ERP Framework"

odoo:
  version: "18.0"
  edition: community
  container_name: odoo_factory_system

database:
  engine: postgresql
  version: "16"
  default_db: odoo
  test_db_prefix: odoo_test_

localization:
  country: EG
  currency: EGP
  accounting_localization: l10n_eg

paths:
  vendor_addons: addons
  custom_addons: custom
  skills: skills/odoo-factory-engineer
  docs: docs
  metadata: .factory

policies:
  vendor_code_read_only: true
  allow_test_modules_in_production: false
  require_tests_for_customization: true
  require_docs_update: true
  prohibit_direct_sql_ddl: true
  unclassified_modules_blocked: true
```

### 4.3 Classification Taxonomy (`.factory/module_policy.yml`)
Allowed classifications:
1. `CORE`: Fundamental ERP components.
2. `OPERATIONS`: Operational extensions (quality, scrap, work centers).
3. `ADVANCED`: Advanced planning, DDMRP, multi-level routing.
4. `INFRASTRUCTURE`: Server tools, queues, base utilities.
5. `INTEGRATION`: Connectors, external sync, APIs.
6. `UI`: Web enhancements, themes, views.
7. `DEV`: Developer tools, profiling.
8. `TEST`: Testing modules (strictly forbidden in production profiles).
9. `HARDWARE`: Specialized equipment (VLM, lifts, barcode terminals).
10. `LEGACY`: Deprecated modules during transition.
11. `UNCLASSIFIED`: Default for newly discovered modules (blocked from production).

### 4.4 Capability Engine (`.factory/capabilities.yml`)
Explicit relationships defining capability contracts:
```yaml
capabilities:
  manufacturing_quality:
    status: approved
    classification: OPERATIONS
    requires:
      - manufacturing
      - inventory
    modules:
      required:
        - quality_control_oca
        - quality_control_mrp_oca
      optional:
        - quality_control_stock_oca
    conflicts: []
    profiles:
      - operations
      - advanced
      - full
    tests:
      - GS-005
      - GS-010
    documentation:
      - docs/functional/quality.md
```

### 4.5 Install Profiles as Single Source of Truth (`.factory/install_profiles.yml`)
`.factory/install_profiles.yml` is the sole authoritative definition. `scripts/factory/generate_profiles.py` generates or validates `custom/factory_profile_*` manifests.
```yaml
profiles:
  core:
    description: "Minimal viable factory ERP"
    capabilities:
      - sales
      - purchasing
      - inventory
      - manufacturing
      - accounting
      - security_baseline

  operations:
    description: "Core ERP plus factory floor operations and quality"
    extends: core
    capabilities:
      - manufacturing_quality
      - scrap_management
      - background_jobs

  advanced:
    description: "Operations plus advanced planning and DDMRP"
    extends: operations
    capabilities:
      - ddmrp
      - advanced_bom
      - advanced_replenishment

  full:
    description: "All production-approved capabilities"
    extends: advanced
    capabilities:
      - advanced_warehouse
      - audit_logging
```

### 4.6 Expanded Discovered Metadata (`.factory/generated/module_catalog.json`)
Generated by `scripts/factory/scan_modules.py`:
* `technical_name`, `display_name`, `repository`, `path`, `version`, `license`, `category`, `summary`
* `depends`, `auto_install`, `installable`, `application`, `external_dependencies`
* `ownership` (`vendor` vs `custom`), `classification`, `capabilities`
* `odoo_version`, `edition_requirement`, `source_commit`, `source_branch`, `status`, `risk`

### 4.7 Directed Dependency Graph with Cycle Detection
`scripts/factory/build_graph.py` produces `.factory/generated/dependency_graph.json` and performs:
* Dependency resolution
* Cycle detection (errors loudly on cyclic dependencies)
* Missing dependency detection
* Unavailable addon detection

## 5. Safe Legacy Relocation Strategy

### Phased Migration
* **Phase 3A: Relocate without renaming**
  * `git mv addons/manufacture/clothing_factory_demo custom/clothing_factory_demo`
  * `git mv addons/server-tools/odoo_factory_all custom/odoo_factory_all`
  * Preserves Odoo technical module names, database IDs, and Git history.
* **Phase 3B: Introduce replacement modules**
  * Create `custom/factory_profile_core`, `operations`, etc.
  * Create `custom/factory_demo` (Universal Generic Demo).
* **Phase 3C: Deprecate legacy modules**
  * Mark `custom/odoo_factory_all` and `custom/clothing_factory_demo` as legacy.
* **Phase 3D: Controlled migration & retirement**
  * Deprecate once new profiles pass Golden Scenario tests.

## 6. Golden Scenario & Cross-Cutting Suites

### Transactional Business Flow (GS-001 to GS-014)
1. **GS-001: Product Master** (Routes, BOM, UOM, costing parameters)
2. **GS-002: Sales Demand** (Customer quotation & confirmation)
3. **GS-003: Availability & Procurement Demand** (Stock reservation check & replenishment triggers)
4. **GS-004: Purchase & Vendor Receipt** (RFQ, PO, vendor receipt)
5. **GS-005: Incoming Quality** (Inspection gate: Pass, Hold, Return to Vendor)
6. **GS-006: Inventory & Lot Tracking** (Internal movement, lot allocation, traceability)
7. **GS-007: Manufacturing Order** (Demand generation, material staging, reservation)
8. **GS-008: Work Orders** (Work center dispatch, time tracking, routing progress)
9. **GS-009: Scrap & Rework** (Scrap reason code recording, rework loop)
10. **GS-010: Finished Goods Quality** (Inspection gate before stock intake)
11. **GS-011: Delivery** (Outbound picking, packing, shipping validation)
12. **GS-012: Customer Invoicing & Accounting** (Account move generation, tax, reconciliation)
13. **GS-013: Customer Return & Triage** (RMA receipt, inspection: restock / rework / scrap)
14. **GS-014: Automated Replenishment** (Reordering rule trigger upon stock dip)

### Cross-Cutting Validation (GX-001 to GX-004)
* **GX-001: Security & Roles** (Role-based access, approval tiers, record rules)
* **GX-002: Reports & Documents** (QWeb PDF rendering: MO card, Pick list, Invoice)
* **GX-003: Queue Job & Async Processing** (Background job worker execution)
* **GX-004: Audit Logging & Traceability** (Audit trails for critical business actions)

## 7. Migration Architecture (`docs/development/migrations.md`)

* **Compatibility Classification:** Backward-compatible (non-breaking) vs schema change (breaking).
* **Execution Flow:** `pre-migration` -> `core upgrade` -> `post-migration` -> `data validation`.
* **Prohibition:** Agents must NEVER use `DROP COLUMN`, `DELETE FROM`, or direct raw SQL DDL/DML to resolve upgrade conflicts without an approved migration plan.

## 8. Definition of Done & Spec-Kit Synchronization

Every substantive feature or bugfix requires:
1. Implementation Code in `custom/**`
2. Automated Unit / Impact Tests passing
3. `.factory/` metadata & schema validation passing
4. Human documentation updated in `docs/**`
5. Architecture Decision Records (`docs/architecture/adr/`) added for architectural changes
6. Spec-Kit updated and synchronized
